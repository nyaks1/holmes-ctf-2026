# F4: Lua obfuscation CTF methods

Angle A4 · SilentDividend `api.txt` (Luraph-style Lua VM) · 2026-09-17 · confidence: high for methodology, medium for this sample’s exact cipher

## Bottom line

Luraph/VM-obfuscated Lua used in malware CTFs is almost never fully recovered by generic decompilers alone. Static/semi-static string recovery is a three-step pipeline: (1) fingerprint the obfuscator family from the outer wrapper + string-table shape, (2) locate and reconstruct the string decoder (custom base64 / XOR / RC4 / positional XOR), (3) decode offline without executing the VM payload. Full LuaJIT execution of `api.txt` is reserved for disposable VMs after static methods fail; the analyst host must not run `luajit.exe api.txt`.

## 1. Identifying the obfuscator

Structural fingerprints beat branding. Commercial and game-oriented Lua obfuscators leave recoverable outer shells:

| Family | Typical fingerprint | Notes |
|--------|---------------------|--------|
| **Luraph** (incl. LPH / Luraph V12+) | `return(function(...)local z={` … string table … VM loop; heavy `_G`/`load`/bytecode; often ships with `lua51.dll`/LuaJIT | Matches SilentDividend `api.txt` head |
| **Prometheus** (Lua VM) | Distinct `Luraph`-unlike VM, Roblox-oriented, `getfenv`/`loadstring` chains | Common in game CTFs, less Electron malware |
| **Ironbrew / Ironbrew2** | Custom bytecode VM, large opcode table, string pool often not `Q`/`n` tagged | |
| **PSU / custom game obfuscators** | Variable; often simpler string table + base64 | |
| **Hand-rolled / packer** | `return(function(...)` + local table but no known VM loop | Still treat as decoder-bearing |

**SilentDividend markers (local sample):**
- Head: `return(function(...)local z={` — IIFE wrapper + single string table `z`
- Table entries mixed: `Q…` often standard-base64 shaped (`==` padding), `n…` often non-padded, high-entropy, custom alphabet / XOR candidates
- Delivery: Electron preload → `powershell … C:\Users\Public\luajit.exe C:\Users\Public\api.txt` → LuaJIT + `lua51.dll` in package
- Conclusion: treat as **Luraph-class VM obfuscator targeting Lua 5.1 / LuaJIT**, not plain `luac` bytecode

**Identification checks (static):**
1. File starts with Lua **source** (`return(function…`) not bytecode magic `\x1bLUA` / LuaJIT `\x1bLJ`
2. One dominant string-table local (`z`, `_`, `L`, `S`, etc.)
3. Two or more string “dialects” in the table (prefix `Q` vs `n` here) → multi-mode decoder
4. Nested functions / opcode dispatch after the table → VM interpreter
5. Residual readable paths (`HTTP`, `powershell`, wallet, Discord, HTB-like) only after decode

## 2. String decoder reconstruction (static / semi-static)

### 2.1 Extract the table carefully
- Do **not** use naive `r'"…"'` when entries contain escaped quotes (`n$d\"Rqd…` in this sample). Prefer a Lua-aware scanner or long-bracket awareness.
- Preserve escapes; many Luraph tables store raw bytes as `\ddd` / `\xHH` / custom.

### 2.2 Locate the decoder function
Typical pattern after `local z={…}`:
- A function `d(i)` / `D(index)` that indexes `z[i]` then transforms
- Call sites: `d(12)`, `z` + arithmetic, or opcode handler in the VM loop

Semi-static triage order:
1. Rip every quoted/long string into a corpus
2. Classify by prefix/charset/length/padding
3. Hunt for the transform body (base64 alphabet, XOR key constants, loop bounds, `string.byte/char/rep/sub`)
4. If the transform is closed-form (no integrity checks), **port it to Python** and batch-decode the table offline — no Lua needed

### 2.3 Encoding modes to try (priority order for this sample)

Observed local sample split:
- **`Q`-prefixed + `=` padding** → standard or custom base64; try full-string b64 *and* strip-first-char b64 (prefix may be alphabet noise, not a tag)
- **`n`-prefixed, no padding, printable-high-entropy** → candidates:
  1. Single-byte XOR (brute 0x00–0xFF on `n…[1:]` or full string)
  2. Positional XOR (`i`, `i+const`, `i % 256`)
  3. Custom base64/alphabet remap (Luraph often reorders alphabet; derive from known plaintext like `http`, `powershell`, `HTB{`)
  4. RC4 with short key; Vigenère
  5. Nested: b64 then XOR, or XOR then b64
- **Longest `n…` entry (~2800 chars)** may be second-stage bytecode or a concatenated blob — try `luajit -bl` / `\x1bLJ` after decode; treat as high-risk payload

**Known-plaintext key recovery:** CTF flags, C2 paths, and Windows paths (`C:\Users\Public`, `luajit`, `HTB{`) are excellent crib material for alphabet/XOR recovery.

### 2.4 What generic decompilers will / will not do
- **unluac / luadec on the outer file:** useless for *strings* if the payload is VM-obfuscated source — they decompile/disassemble the VM, not the plaintext
- **unluac / luadec / ChunkSpy on recovered bytecode** (if decode yields `\x1bLUA` or after `luajit -b`): very useful to recover real logic and residual plaintext constants
- **luadec (viruscamp):** Lua 5.1 primary (matches lua51.dll); `luadec -dis` disassembles; `-pn` prints nested function tree; `-f 0_1 -ns` isolates a nested function (useful to peel VM layers). Experimental 5.2/5.3. [GitHub: viruscamp/luadec]
- **unluac:** Java decompiler for official Lua 5.1–5.3 bytecode; weaker on LuaJIT and on commercial VMs
- **ChunkSpy:** Lua 5.1 bytecode disassembler (bundled in viruscamp/luadec tree) for instruction-level VM mapping
- **LuaJIT tooling:** `luajit -bl file` / `-b` for LJ bytecode listings when you have a `.luac`/binary chunk
- **Custom:** Python reimplementation of the decoder is the CTF workhorse; Ghidra/IDA on `lua51.dll` is rarely needed (VM is usually pure Lua, not native)

## 3. Sandboxed execution practices (semi-static)

Preferred path when static decode is incomplete: **run only the decoder**, not the full payload.

1. **Cut the decoder** (function + string table) out of the obfuscated source
2. Execute under Lua 5.1/LuaJIT **in a restricted environment**:
   - Strip/replace: `os`, `io`, `require`, `dofile`, `load`, `loadstring`, `package`, `debug`, `bit`, FFI
   - Provide stub `print` that logs to a file
   - Deny network; empty `package.path/cpath`
3. Tools:
   - Hand-built Lua sandbox script
   - Python `lupa` (if installed) with a locked `_G`
   - Offline copy of LuaJIT **only inside a disposable VM**, never the analyst host with the malware’s own `luajit.exe`/`lua51.dll` if those are untrusted
4. Dump every decoder return value to a transcript for flag regex (`HTB{`, hex, base58, etc.)

## 4. When disposable-VM full execution is required

Escalate to a **disposable, network-isolated VM** only if:
- Decoder is entangled with VM state, integrity checks, or anti-tamper (checksum of source, `debug.getinfo` probes)
- Strings are assembled at runtime from pieces across the VM loop
- Behavior (wallet steal, C2, file drop) is the only place flags appear
- Recovered intermediate blobs are LuaJIT bytecode that only the provided interpreter can load safely

VM checklist (forensics, not host):
- Snapshot before run; no shared clipboard/folders with analyst host
- Fake wallet / decoy secrets in expected paths (`%USERPROFILE%`, browser profiles)
- Hosts-file blackhole + packet capture for C2
- Run **the package’s** `luajit.exe` only inside the VM, never on the CTF analysis host
- Prefer extracting decoder + table out first; full run is last resort

## 5. Application to SilentDividend (actionable)

1. Re-scan `nsis\extraResources\api.txt` with a Lua-aware string extractor (escapes matter)
2. Split corpus by `Q` vs `n` prefixes; test standard/urlsafe b64 on all Q-shaped strings; custom-alphabet if low yield
3. On `n` corpus: 1-byte then 2-byte XOR, positional XOR, then b64+XOR stacks; use known cribs from Electron preload (`powershell`, `Public`, `luajit`, blockchain RPC URLs)
4. Grep decoded set for `HTB{`, addresses, IPs, Discord/Telegram tokens, registry keys — flags may be **assembled** not stored whole
5. If a second-stage LuaJIT blob emerges, disassemble with luadec/ChunkSpy/LuaJIT `-bl` **offline**; do not `require`/run it on host
6. Only if decoder extraction fails: disposable VM run of full `api.txt` with sandboxing

**Do not:** execute `luajit.exe api.txt` on the analysis host (preload already shows this is the malware second stage).

## 6. Tool index (CTF/forensics)

| Tool | Role | Best for |
|------|------|----------|
| unluac | Official Lua 5.1–5.3 bytecode decompiler | Recovered `.luac` from non-JIT stages |
